# 文档维护规则

## 职责与事实来源

| 位置                                          | 职责                                     |
| --------------------------------------------- | ---------------------------------------- |
| [README](../README.md)                        | 用途、运行环境、可执行命令与文档入口     |
| [AGENTS](../AGENTS.md)                        | Agent 执行边界与交付规则，只引用详细规范 |
| [文档地图](index.md)                          | 工程文档导航与 OpenSpec 入口             |
| `docs/` 工程指南                              | 当前架构、代码约定、开发流程与测试指导   |
| [OpenSpec 当前规格](../openspec/specs/)       | 经变更流程同步的功能规格                 |
| [OpenSpec 活动变更](../openspec/changes/)     | 提案、规格增量、技术设计、任务与验证记录 |
| [OpenSpec 归档](../openspec/changes/archive/) | 已完成变更的历史                         |

功能规格与变更的唯一维护位置是 `openspec/`。工程文档可以解释现有技术边界和未接入状态，不复制用户行为的完整验收标准。不创建 `docs/specs/`、`docs/changes/` 或本地 Spec、提案、ADR 模板。

实现细节以源码为准，预期行为以 OpenSpec 规格和相关变更中的已确认要求为准。初始化时规格目录为空；尚未迁移的行为以用户已确认要求和原需求输入为依据，结合代码核对，不能只从代码反推正确需求。历史材料保留为输入，避免同时维护两套行为规则。

## 更新矩阵

| 改动                                   | 检查并同步                                  |
| -------------------------------------- | ------------------------------------------- |
| 环境、启动、构建与打包命令             | README；涉及验证时同步测试指南              |
| 目录、命名、代码归属与依赖方向         | 项目规范                                    |
| 服务注册、数据流、存储、IPC 或模块边界 | 架构；本次设计放在 OpenSpec `design.md`     |
| 用户可见行为、业务规则或兼容行为       | OpenSpec 变更及其当前规格，按流程同步和归档 |
| 测试组织、命令或验证要求               | 测试指南                                    |
| Agent 工作边界与协作流程               | AGENTS、开发流程和本文                      |
| 新工程文档或导航入口                   | 文档地图与相关文档链接                      |

## 文件、链接与状态

- 新工程文档采用小写英文和连字符；既有中文需求与历史文件不批量重命名。
- 仓库内引用用 Markdown 相对链接。必需入口只能指向存在且纳入版本控制的文件或目录；本地忽略材料用代码路径标明可选性。
- 计划、未接入和未验证能力明确标记；不把历史本机验证当作当前回归结果。
- OpenSpec 活动目录为 `<change-name>`，归档目录为 `YYYY-MM-DD-<change-name>`；schema、状态和模板以 CLI 实际输出为准。
- 用户已明确确认的要求无需重复批准；关键行为歧义先澄清，未回复不表示同意。
- 文档与相关代码、测试在同一本地 commit 中提交，不夹带用户原有改动。只有工程文档初始化时，不凭空建立功能变更或回填完成记录。
